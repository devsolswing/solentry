# Trading Bot — Railway-hosted multi-user trading app

A public, small-community trading app. **Separate from** James's private
live 5-bot engine (Railway project `zealous-caring`) and from SolSwing.
Never mix those in. James's personal Phantom wallet is never touched —
every app user gets their own separate app wallet generated by the app.

## What it does

- **SolEntry login page**: red/gold neon design from James's screenshot
  (Shiba hero, "SolEntry — Automated Trading Tool", email + password
  fields with show/hide eye toggle, Login button, Create Account link,
  Donate card, Contact Us card, Version 1.00, J. Gordon signature).
  Every button works and visibly responds.
- **Donations**: the login page's Donate card has a **Connect Wallet**
  button (Phantom connector) + an amount (SOL) input + Send Donation.
  No token/network/amount dropdowns. The donor connects their own
  Phantom wallet and approves the transfer in Phantom; the SOL goes to
  the project's donation wallet (one wallet, generated once by the
  server, encrypted like user wallets — NOT James's personal Phantom
  wallet). The server only records the confirmed donation (donor,
  amount, signature). Every confirmed donation appears on the
  admin-only `/admin/donations` page — that page IS the notification
  for James. Email notification is NOT configured (no mail service).
- **Accounts**: username + password signup/login. Passwords hashed with
  scrypt (per-user salt). Sessions are signed cookies. Every query is
  scoped by `user_id` — users can never see each other's data. Login is
  rate-limited (5 failed tries → 15-minute lockout).
- **Per-user wallet**: a fresh Solana keypair is generated at signup and
  encrypted with AES-256-GCM (`ENCRYPTION_KEY`). Only the public address
  is ever shown. Top wallet button (💰) offers Withdraw / Send / Deposit.
- **Sends are two-step, always**: create a send intent → confirm screen
  (destination, amount, token, estimated fee) → only then it signs and
  sends. The server signs with the stored key; the signature is recorded
  in the user's activity log.
- **Paper trading**: $10,000 fake money per user. Buy/sell at the current
  price; portfolio + activity log. Prices come from the CoinGecko public
  API server-side, with a clearly-labeled baked snapshot when the API is
  unreachable (stale prices are never presented as live).
- **Real trading (approval-gated in v1)**: per-user bots (name, strategy
  Careful/Balanced/Bold, coins, buy size %, stop loss %, max open trades
  1–5, mode paper or real). Each bot gets its own API token (random,
  stored hashed, shown once). The bot only proposes trades; the user
  approves each one in-app. Approving a buy/sell proposal records the
  decision — on-chain swaps are not executed in v1 (labeled in the UI).
  Approved SOL transfers go through the normal two-step send confirm.
- **Silent trading (opt-in per bot, off by default)**: when a user
  explicitly switches a bot to silent (through a confirm screen — never
  a bare toggle flip, never on at creation), the bot trades on its own
  in the background, with no per-trade approval. It only trades within
  the bot's limits (buy size %, stop loss %, max open trades, never more
  than the user's balance — paper cash for paper bots, app-wallet SOL
  for real bots). Every buy, sell, and skipped trade (with the reason)
  is written to the user's activity log. Turning silent off stops the
  bot on the next loop tick. The loop runs as a daemon thread inside the
  web process when `SILENT_LOOP_ENABLED=1` (see "Silent trading loop"
  below). Real bots in silent mode currently SKIP every trade with
  "real swap not available in v1" — the app has no on-chain swap path
  yet, so nothing is faked. Stop loss is enforced on every evaluation.
- **In-app assistant**: a deterministic command parser + knowledge base
  (labeled as the app assistant, not a language model). Understands
  "edit bot", "delete bot", "create bot", "send X SOL to …", "what is my
  balance", "show my bots", "show my wallet", "how does paper trading
  work", "turn on silent trading for <bot>" (asks for confirmation
  first), "turn off silent trading for <bot>" (applies at once),
  "is silent trading on". Sends never execute directly — they open the
  confirm flow. Deletes ask for confirmation first.
- **Railway provisioning (gated, off by default)**: `tradingbot/
  railway_provision.py` can create a per-user bot service via Railway's
  public GraphQL API, but only when `RAILWAY_PROVISIONING=1` AND
  `RAILWAY_TOKEN` are both set. It is never wired into signup and never
  runs in tests. It logs/returns only service and variable NAMES, never
  values. **Per-user bot provisioning consumes Railway credits — nothing
  spins up without an explicit admin action.**

## Run it locally

```bash
python -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env   # then fill in SESSION_SECRET + ENCRYPTION_KEY
.venv/bin/python run.py
# open http://localhost:8000
```

Generate the secrets with:
`python -c "import secrets; print(secrets.token_hex(32))"`

## Tests

```bash
.venv/bin/python -m unittest discover -s tests -v
```

Tests use throwaway keys only and a mock RPC. **No real SOL ever moves
in tests.** Real devnet sends and the Railway deploy are NOT verified by
this build — see "What was verified" in the delivery report.

## Deploy to Railway (admin)

1. Create the GitHub repo (James creates it — the Muse GitHub App
   cannot create repos) and push this directory to `main`.
2. In Railway, create a project from that repo (Nixpacks detects
   `requirements.txt` + `Procfile`; start command `python run.py`).
   No Dockerfile needed; no native build tools required.
3. Set service variables (names only — values are yours):
   `SESSION_SECRET`, `ENCRYPTION_KEY`, `NETWORK=devnet`.
   Optional: `RPC_URL`, `DATABASE_PATH`, `PAPER_START_CASH`,
   `ADMIN_USERNAME` (who may see `/admin/donations`; default is the
   first registered user).
   Leave `RAILWAY_PROVISIONING=0` (default) unless you deliberately
   enable per-user bot provisioning — each provisioned service costs
   Railway credits.
4. Deploy. Check `/health` returns `{"ok": true, "network": "devnet"}`.
5. Silent trading loop: set `SILENT_LOOP_ENABLED=1` on the web service
   to run the loop as a daemon thread inside the web process (interval
   `SILENT_LOOP_INTERVAL_SECONDS`, default 60). The start command stays
   `python run.py`. A separate worker service is NOT used: the SQLite
   file lives on the web service's volume and a second service cannot
   see it. `python -m tradingbot.silent_loop --once` runs one iteration
   standalone (for smoke tests and a future shared-database setup).
   The loop only ever trades for bots the user explicitly switched to
   silent; it re-reads the flag every iteration, so turning silent off
   stops the bot on the next tick.

Notes: the SQLite file lives on the service disk (ephemeral on Railway
redeploys unless a volume is attached — attach a Railway volume at the
`DATABASE_PATH` location before real users sign up). For mainnet, set
`NETWORK=mainnet` only on explicit config, after a devnet shakedown.

## Security rules (do not weaken)

- Never log, print, or return a private key, password, session secret,
  encryption key, or token value.
- Never store a secret in code or in the repo. `.env.example` has
  placeholders only.
- Never move real SOL on an ambiguous instruction. Sends always need
  the confirm step.

Note: the login hero image is embedded as a base64 data URI in `tradingbot/templates/login.html` (GitHub snapshot pushes accept text only). The master file is `tradingbot/static/hero-shiba.jpg` — if you replace it, re-embed it the same way.
