# Trading Bot — Railway-hosted multi-user trading app

A public, small-community trading app. **Separate from** James's private
live 5-bot engine (Railway project `zealous-caring`) and from SolSwing.
Never mix those in. James's personal Phantom wallet is never touched —
every app user gets their own separate app wallet generated by the app.

## What it does

- **SolEntry login page**: red/gold neon design from James's screenshot
  (Shiba hero, "SolEntry — Automated Trading Tool", email + password
  fields with show/hide eye toggle, Login button, Create Account link,
  Donate card, Contact Us card, Version 1.00, J. Gordon signature).
  Every button works and visibly responds.
- **Donations**: the login page's Donate card has a **Connect Wallet**
  button (Phantom connector) + an amount (SOL) input + Send Donation.
  No token/network/amount dropdowns. The donor connects their own
  Phantom wallet and approves the transfer in Phantom; the SOL goes
  ONLY to the recipient in the `FEE_RECIPIENT_PUBKEY` env var — the
  same single wallet that receives the 3.65% trading fee. There is no
  app-generated donation wallet any more (any `donation_wallet` row
  left from before is purged at startup). The page shows only the
  first 5 characters of the recipient address + `*****` — never the
  full address. The donor's browser fetches the full address from
  `/api/donate/info` when Send is tapped so it can build the
  transfer, and Phantom shows the full destination when the donor
  approves — the masking is the page display, not the signed
  transaction. The server only records the confirmed donation
  (donor, amount, signature). Every confirmed donation appears on
  the admin-only `/admin/donations` page — that page IS the
  notification for James. Email notification is NOT configured (no
  mail service).
- **Accounts**: username + password signup/login. Passwords hashed with
  scrypt (per-user salt). Sessions are signed cookies. Every query is
  scoped by `user_id` — users can never see each other's data. Login is
  rate-limited (5 failed tries → 15-minute lockout).
- **Recovery question**: on the Settings page a user sets a recovery
  question + answer + optional hint. The answer is hashed with scrypt
  (per-user salt), never stored in plaintext, never logged. Forgot
  password asks for the username, then shows the question and hint —
  the right answer lets the user set a new password (and clears any
  login lockout). 5 wrong answers lock the account for 15 minutes,
  like too many wrong passwords. If no question is set, the page says
  plainly that recovery is not set up — it never reveals whether the
  account exists.
- **Passkeys (WebAuthn, optional)**: users can register a passkey from
  Settings and sign in with it from the login page ("Sign in with
  passkey") — fingerprint, face, or device PIN. Password login still
  works; a passkey is an option, not a replacement. Only the public
  key is stored (`passkey_credentials` table); the private key never
  leaves the user's device. Challenges are server-issued, single-use,
  and expire after 5 minutes. RP ID / name / origin come from env
  vars (`WEBAUTHN_RP_ID`, `WEBAUTHN_RP_NAME`, `WEBAUTHN_ORIGIN`) —
  the RP ID must match the live domain or the browser rejects the
  ceremony. If the browser has no passkey support, the button says so
  instead of failing silently.
- **Mode chooser + full paper/real split**: after every sign-in a
  popup appears on the landing page (the wallet) with the SolEntry
  logo — **Demo trading** or **Real trading — devnet** (labelled
  devnet so nobody mistakes it for mainnet). The choice becomes the
  user's `active_mode` and sticks until the HUD switch changes it.
  The answer is remembered in the database (`users.mode_chosen_at`)
  as well as the session, so a dropped session flag alone can never
  make the chooser reappear mid-session; signing in clears it, so
  the chooser still shows once after each sign-in. Paper and real are completely
  separate: every dashboard / P&L / bots / wallet query is filtered
  by the active mode (`activity.mode`, `bots.mode`,
  `bot_positions.mode`, `real_holdings` vs `paper_holdings`), and each
  page is labelled with the mode it shows. The silent loop only ever
  runs bots whose mode matches the bot, and real bots only on pump.fun
  (see below).
- **Platform picker + per-platform wallets**: the bot form has a
  Platform selector — **pump.fun, Phantom, pumpSwap** — replacing the
  old "coins to watch" field. Each platform has a **Create Wallet**
  button that makes that platform's wallet automatically (fresh
  keypair, AES-256-GCM encrypted like the app wallet, one wallet per
  platform per user — if one already exists its address is shown
  instead). Honest mapping: pump.fun and pumpSwap have no accounts of
  their own, so their wallets live in the app; the Phantom wallet is
  generated by the app for import into Phantom (plain import steps
  shown — a wallet cannot be created inside Phantom itself) and its
  private key is shown **exactly once** at creation, never again.
  The platform is stored on the bot (`bots.platform`); the silent
  loop refuses real trading on any platform other than pump.fun
  ("real trading on X is not live yet") and the executor is never
  called for those bots.
- **Login first, no landing page**: visiting `/` goes straight to the
  login screen (logged-in users go to `/wallet`). The login screen is
  the red/gold design — Shiba door hero, "TRADE SMARTER... AUTOMATE
  BIGGER...", Email Address + Password, Login, Create Account, Donate
  (Connect Wallet — no token/network/amount dropdowns), Contact Us,
  Version 1.00, J. Gordon signature — plus passkey sign-in and the
  forgot-password link.
- **Wallet is the homepage (fox layout)**: after sign-in (and the mode
  chooser) the app lands on the Home page — a red fox-head-with-cigar
  logo, TOTAL PORTFOLIO VALUE (paper total in paper mode, real SOL
  value in real mode), 24h change from recorded snapshots only
  ("—" with no snapshots — never invented), a chart with a range
  selector (1H/24H/1W/1M/1Y/All, from recorded snapshots only) and a
  **Log** button (opens the Logs page, Page 11), big **BUY** and **SELL** buttons that open
  the quick Buy/Sell pop-up, **Send** and **Receive** buttons below
  them (Receive opens a window with the app wallet address + copy),
  then the **HOLDINGS** list — the coins held in the active mode in
  fine print (real name + ticker, amount held, value) in a 1/4-screen
  window that scrolls internally, with a small-print summary (coin
  count + total, paper cash in paper mode). The home screen has no
  X (back) button: on the homepage it looped (back -> login page ->
  instant redirect to /wallet), so the homepage kept re-applying
  itself; the X stays on Bots and Trenches, where going back makes
  sense. Tapping a coin opens its
  **coin detail page**: a market chart with 24hr / 1day / 1w / 1m / 1y
  / all-time ranges (CoinGecko market_chart, real data or "No data
  yet" — never invented; 24hr and 1day are the same 1-day window),
  24h high and low (from the 24h chart series), buyers vs sellers %
  (DexScreener 24h buy/sell txn counts, "—" when the feed has none),
  a **live chart** that ticks every second while the page is open
  (`GET /api/coins/<id>/tick` — real feed prices only, never
  invented; a failed tick keeps the last real price and its time,
  and polling pauses while the tab is hidden), and **Send / Receive
  / Buy / Sell**, each opening its own window (Send reuses the
  two-step confirm flow and returns to the coin page; Buy / Sell /
  Sell all — all in SOL). A **Trenches** card on
  the home page (and on the Bots page) opens the **Trenches page**:
  black + gold theme with a black/gold fox logo, the top 10 fresh
  pump.fun / PumpSwap tokens by 1h gain (price + 1h gain per row, best
  1h gain first, from the DexScreener feed — "Trenches unavailable
  right now" when the feed does not answer); tapping a trenches token
  opens the coin popup with the same **Buy / Sell / Sell all (in SOL)
  + Send / Receive** as the detail page. The wallet itself lives on
  **/wallet/details** — deposit / send / withdraw / platform wallets
  in real mode, paper balance in paper mode, plus the Dogewifhat door
  artwork and a Canadian flag (the flag also shows on the home page).
- **Coins list + coin popup + trenches**: the Coins page lists ONLY
  the coins you hold in the active mode (name + ticker + current
  price + P&L; a fresh user sees "You hold no coins" instead of the
  whole price list), and tapping one opens its detail page. A small
  **Buy or Sell Coin** button below the list opens a full-screen
  pop-up: type a coin name and live results appear as you type
  (`/api/coins/search` — the price list plus DexScreener token
  search, Solana pairs only, never invented; a feed that does not
  answer says so), then enter an amount in **$ or tokens** at the
  live price and Buy / Sell / Sell all through the same coin
  endpoints as the popup and detail page (buy also accepts a token
  amount, sell also accepts a $ amount — both convert at the
  server's own live price, never at a browser-sent one). A **↻
  Refresh live data** button at the top of the page clears the
  cached prices, on-chain balance and trenches list and records a
  fresh portfolio snapshot, so every chart re-renders from live
  data instead of up-to-60-second-old values. Tapping a
  trenches token opens the coin popup with the same **Buy / Sell /
  Sell all (in SOL) + Send / Receive** as the detail page. Send keeps
  the two-step confirm and comes back to the coins screen; Receive
  shows the wallet address with copy. After ANY popup or detail-page
  action a confirmation page states the results (what happened,
  amounts, new balance/position) with a **Back to coins** button.
  Paper buys/sells run in the paper ledger (SOL amounts convert at the
  current SOL price); real buys/sells route through the existing
  pump.fun executor with the same guards as the silent loop (devnet
  only, real bot required, amount within the bot's limits, rules
  engine allows it) — a refusal is shown plainly and nothing is
  filled. No second execution path exists. The old dashboard Quick buy
  card and its /paper/buy + /paper/sell endpoints are gone — buys and
  sells live only in the coin popup, the coin detail page, and the
  quick Buy/Sell pop-up.
- **One-screen UI + HUD**: the app is a phone-first shell — the page
  never scrolls, long lists scroll only inside fixed-height panels,
  and a fixed bottom HUD switches pages: **Home, Bots, Wallet,
  Settings**, plus the Paper/Devnet mode switch in the topbar. The
  **Bots page** shows the SOL balance + USD with an eye (hide/show),
  the fox logo, + create / − delete (server-rendered confirm page,
  never a native confirm()) / Edit Bot, and an **Active Bots**
  carousel with < > arrows — each card shows the bot's real name,
  silent status, id, created date, strategy, buy size and stop loss
  (no per-bot 24H PNL — the app cannot compute it, so it is never
  shown). Red + gold theme throughout (Kraken Pro iOS layout,
  original SolEntry logo); the Trenches page alone is black + gold.
- **Per-user wallet**: a fresh Solana keypair is generated at signup and
  encrypted with AES-256-GCM (`ENCRYPTION_KEY`). Only the public address
  is ever shown. Top wallet button (💰) offers Withdraw / Send / Deposit.
- **Sends are two-step, always**: create a send intent → confirm screen
  (destination, amount, token, estimated fee) → only then it signs and
  sends. The server signs with the stored key; the signature is recorded
  in the user's activity log.
- **Paper trading**: $100 CAD fake money per user. Buy/sell at the current
  price; portfolio + activity log. Prices come from the CoinGecko public
  API server-side, with a clearly-labeled baked snapshot when the API is
  unreachable (stale prices are never presented as live). Buy/sell
  lives in the coin popup and the coin detail page (all amounts in
  SOL; paper amounts convert at the current SOL price): a paper buy
  with a bot records the coin as that bot's position, so the silent
  loop governs it by the bot's rules once its silent trading is on.
  The top corner shows the balance with a Paper/Devnet switch beside
  it: Paper shows the paper portfolio value, Devnet shows the app
  wallet's on-chain SOL balance (cached 60 seconds; an unreachable RPC
  shows "unavailable", never a guessed number). The switch is a plain
  form button — no JavaScript — and the choice is stored per user.
- **Deleting a bot asks on its own page**: the edit page and the bots
  list link to a confirm page ("Delete bot 'X'?") instead of the
  browser's confirm() dialog, which in-app browsers often never show
  (the button then looked dead). Deleting a bot un-manages its open
  positions — the coins stay in the paper holdings, sellable by hand.
- **Real trading (approval-gated in v1)**: per-user bots (name, strategy
  Careful/Balanced/Bold, coins, buy size %, stop loss %, max open trades
  1–5, mode paper or real). Each bot gets its own API token (random,
  stored hashed, shown once). The bot only proposes trades; the user
  approves each one in-app. Approving a buy/sell proposal records the
  decision — on-chain swaps are not executed in v1 (labeled in the UI).
  Approved SOL transfers go through the normal two-step send confirm.
- **Silent trading (opt-in per bot, off by default)**: when a user
  explicitly switches a bot to silent (through a confirm screen — never
  a bare toggle flip, never on at creation), the bot trades on its own
  in the background, with no per-trade approval. It only trades within
  the bot's limits (buy size %, stop loss %, max open trades, never more
  than the user's balance — paper cash for paper bots, app-wallet SOL
  for real bots). Every buy, sell, and skipped trade (with the reason)
  is written to the user's activity log. Turning silent off stops the
  bot on the next loop tick. The loop runs as a daemon thread inside the
  web process when `SILENT_LOOP_ENABLED=1` (see "Silent trading loop"
  below). Real bots in silent mode currently SKIP every trade with
  "real swap not available in v1" — the app has no on-chain swap path
  yet, so nothing is faked. Stop loss is enforced on every evaluation.
- **In-app assistant**: a deterministic command parser + knowledge base
  (labeled as the app assistant, not a language model). Understands
  "edit bot", "delete bot", "create bot", "send X SOL to …", "what is my
  balance", "show my bots", "show my wallet", "how does paper trading
  work", "turn on silent trading for <bot>" (asks for confirmation
  first), "turn off silent trading for <bot>" (applies at once),
  "is silent trading on". It also sets a bot's trading rules from plain
  words — "bot Luna scan pump.fun and pumpswap, buy when a coin gains
  5% in 5 minutes" — shows the parsed rules back in plain words and
  asks for an explicit "yes" before applying them. It understands
  "create the trenches bot", "show rules for <bot>", and "remove rules
  for <bot>", and rug sell commands — "sell everything if the dev
  starts selling", "sell if the price drops 15% in a minute", "add a
  rug rule to bot <name>" — which add the fast-drop exit to a bot's
  existing rules (shown back, "yes" to apply). Sends never execute directly — they open the
  confirm flow. Deletes ask for confirmation first.
- **AI agent + per-bot rules engine (`tradingbot/rules.py`)**: a bot can
  carry a structured rule set (validated JSON): scan sources, scan
  interval, buy signal (metric + window + threshold), sell ladder
  (partial sells at profit targets), trailing stop (% below the peak
  since holding), and a rug sell — sell everything on a fast drop
  (default 15% in about a minute, or 25% in 5 minutes; both
  configurable per bot, 1-minute or 5-minute windows only). The rug
  sell is checked first on every price update, before the stop loss,
  trailing stop and ladder. It is PRICE-based: the DexScreener feed
  cannot see a token creator's wallet, so a dev selling is only
  visible as the price falling — the rule triggers on that fall, never
  on a faked "dev sold" signal. A dev-wallet-sell signal would need
  on-chain transaction monitoring of the creator's wallet, which the
  app does not do. Rules are validated on write and re-validated by the
  loop on every evaluation — a broken rule set means NO trades, never a
  guess. Limits (buy size %, stop loss %, max open trades, balance)
  live on the bot, never in the rules: any rule set carrying a limit
  field is rejected outright, so a rule can never widen a limit. The
  bot's own stop loss % is still enforced as a hard stop on top of the
  rules. Bots without custom rules keep the standard v1 signals.
- **Memecoin build + Trenches preset**: the Bots page has a "Memecoin
  build" section. The Trenches preset (paper, silent off) scans
  pump.fun and PumpSwap every 60 seconds, buys a coin gaining 3.4% in
  a 5-minute window (strongest gainer wins, at most one new position
  per scan), sells 10% at +3% profit and the rest at +10%, and sells
  everything if the price falls 7% below its highest price since
  holding. The rug sell is on by default: sell everything on a 15%
  drop in about a minute, or a 25% fall in 5 minutes — the fast-drop
  exit that gets out before a dev rug finishes (price-based; the feed
  cannot see the dev's wallet). There is NO market-cap filter: a trending coin qualifies
  at any market cap, tiny or huge. It is creatable from the Bots page or by asking the
  assistant ("create the trenches bot"). The trenches feed is
  DexScreener's free public API (no key): latest token profiles +
  pair lookups filtered to pumpfun/pumpswap pairs, with 5-minute price
  moves. The pump.fun frontend API is behind a Cloudflare challenge
  and cannot be read server-side. A feed failure means no trades that
  scan — data is never faked.
- **∆scanner∆ sniper + top-10 wallets watch (`tradingbot/scanner.py`,
  `tradingbot/rules.py`, `tradingbot/silent_loop.py`)**: the scanner
  lives in the Edit Bots form, under the category list next to the
  Memecoin build (category stored as `scanner`, one per user, paper,
  silent off — picking ∆scanner∆ there gives the bot the scanner
  sniper rules; it is also creatable by asking the assistant, e.g.
  "create the scanner bot" or "snipe coins gaining 5% in 3
  minutes"). Its old standalone card on the Bots page is gone — the
  category/strategy pickers are gone too (see builderBot below):
  a scanner bot's rules are set when it is built, and the Edit Bots
  form now edits only name and limits. The
  scanner buys any coin gaining **5%
  in 3 minutes**, scanning every **30 seconds** for gainers and
  keeping track of improving coins (strongest 3-minute gainer wins,
  at most one new position per scan). The 30-second cadence is
  per-bot — other bots keep their own scan interval; the global loop
  interval (`SILENT_LOOP_INTERVAL_SECONDS`, min 10) is unchanged.
  The 3-minute gain is computed from price marks the loop records
  itself (`scanner_marks`, one price per candidate mint per scan):
  the DexScreener feed only provides 5-minute changes, so a coin
  with no mark at least 3 minutes old has no 3-minute gain yet and
  is not bought, never guessed. **Profit ladders** — the scanner
  secures profit on two ladders, picked per position per scan by the
  market regime: **slow market** sells 25% at +3%, +10%, +25%, the
  rest at +50%; **trending market** holds the runners, selling 10%
  at +26%, +50%, +100%, +500%, +1000%, the rest at +10000% or on
  the 7% trailing stop, whichever comes first. **Regime**: trending
  needs all three from the DexScreener feed — 5-minute volume at
  least 2x the average 5-minute pace of the last hour, buys
  outnumbering sells in the last 5 minutes, and a positive 1-hour
  change; anything else (including missing data) is slow. There is
  **no social-media feed** — "community active" is judged from the
  feed's volume and buyers, never guessed. A bad coin is **cut at
  the 7% stop loss** (and the rug sell fires regardless of cost):
  winners run big while losers are capped small, so total profit
  can exceed total losses even when fewer than half the trades win.
  **Top-10 wallets watch**: the loop watches the top 10 holders of
  every held coin through Solana RPC `getTokenLargestAccounts`
  (public RPC, no key): the baseline is the top-10 combined holdings
  the first time the position is watched, tracked upward to the peak
  since holding, and a **10% drop** from that peak sells everything.
  The pump.fun sell pays out in SOL, so the proceeds stay in SOL —
  no extra conversion step. If the RPC cannot serve a mint (or the
  RPC fails), that coin's top-10 watch is skipped for that scan and
  logged — never faked, never guessed. This trigger runs alongside
  the price-based rug sell (either one fires the exit). **Top-10
  concentration triggers** (scanner and trenches bots): alongside the
  10% dump rule, the watch also tracks the top 10 holders' combined
  share of TOTAL token supply, fetched from the same RPC call.
  **(a) Concentration — share reaches 21% → sell everything
  immediately.** **(b) Slow climb — the share rises on 3 consecutive
  15-second checks while it is at least 10% and still below 21% →
  sell 50% to lock profit** as an early rug warning; it fires once
  per climb (any check where the share does not rise resets the
  streak). If the total supply is unknown, the watch is skipped for
  that check — never guessed. The watch runs every **15 seconds** per
  held coin on its own loop, independent of the bot's scan interval;
  the price used for a concentration sell is fetched only once the
  trigger has fired (a missing price means the sell waits for the
  next check, never a guessed price).
- **builderBot — the conversational bot builder
  (`tradingbot/builderbot.py`, `tradingbot/scrubber.py`,
  `tradingbot/ledger.py`)**: pressing **Create Bot** opens a chatbox
  where builderBot asks **simple questions one at a time** — name,
  platform (pump.fun / pumpSwap / Phantom), mode (paper / real
  devnet), market-cap minimum, buy signal (gain % + window), buy
  size %, max open trades, stop loss %, take-profit ladder, trailing
  stop %, top-10 rules, scan interval — each explained in plain
  words (what a stop loss protects, why a market-cap minimum filters
  junk), with sensible defaults offered as tap-to-accept suggestions.
  Answers are parsed deterministically into validated structured
  rules (fail-closed: a bad or ambiguous answer is asked again,
  never a broken bot) and the whole bot is shown back in plain words
  with a **"yes" required before anything is created**. The old
  category and strategy pickers are gone — the bot form is the
  chatbox entry point, and the Edit Bots form now edits only name
  and limits (strategy/category are set when the bot is built).
  builderBot is a **deterministic builder, not a general AI** — it
  turns answers into the bot's rules, and those rules are the code
  the bot runs. It has its own unique immutable **8-digit ID**
  (shown on the chatbox page, same pattern as the signing bot's
  support ID: only INSERT exists, no update path).
  **Trade ledger + W/L**: every trade (buy and sell, paper and real)
  is recorded in the `trade_ledger` table with a unique **8-digit
  trade ID**, a timestamp, bot, coin, side, amount, price, total,
  P&L vs average cost (sells only), win/loss (a break-even trade is
  neither), exit reason, and mode. The bot's page shows wins,
  losses, win rate and net P&L, plus the recent trades. **Auto-
  adjustment**: when a bot is losing — 5 or more closed trades with
  a win rate of 40% or less — builderBot tightens its rules slightly,
  one small step at most once a day: stop loss −1% (floor 3%), then
  buy-signal threshold +0.5% (cap 15%), then buy size −5% (floor 5%).
  It **never** widens buy size, stop loss, max-open or balance
  limits, and never touches real-mode limits upward. Every
  adjustment is logged with the reason (which trades triggered it)
  and shown on the bot's page; the user can reverse it by editing
  the bot. **Security**: builderBot **never has access to wallet
  keys** — its code paths never call the key-decrypt functions and
  never receive key material; only the signing bot (executor) touches
  keys. Its stored data (chat history, per-bot notes, adjustment
  reasons) is **encrypted at rest** with the app's AES-256-GCM
  pattern via ENCRYPTION_KEY. A **scrubber** redacts anything that
  looks like a secret before builderBot stores or logs it: PEM
  private-key blocks, keypair JSON arrays (32+ ints 0–255), long
  base58 strings (80+ chars), 128-hex-char secrets, `xprv…` keys,
  labelled secrets (`password:`, `private key:`, `seed phrase:`,
  …), emails, phone-number shapes, and a message that is only a 12-
  or 24-word lowercase seed phrase. A message that is nothing but a
  secret is refused outright. **Honest limit: the scrubber catches
  known patterns only — it cannot prove an unknown secret format was
  caught.** Never paste a wallet key, seed phrase or password into
  the chatbox; builderBot's working memory is wiped after the bot is
  created (or the chat is cancelled), and deleting a bot purges
  builderBot's stored chats, notes and adjustments for it.
- **Paper reset to $100 CAD + losing-buy analysis + buy filter
  (`tradingbot/analysis.py`, `tradingbot/scanner.py`,
  `tradingbot/rules.py`)**: paper starts at **$100 CAD** fake money
  per user (config `PAPER_START_CASH`, default 100). A one-time
  migration (`paper_reset_100_cad` in `tradingbot/db.py`) resets every
  paper portfolio to $100 CAD cash and clears open paper positions on
  the first start after the update — trade history and P&L snapshots
  are kept as records; real SOL is untouched. The **losing-buy
  analysis** is a section on the Logs page (`/logs`, Page 11, paper
  mode only — there is no separate page or route for it): it pairs
  every paper trade FIFO per coin and shows buy time, coin, bot,
  buy/sell prices, P&L, hold time, exit reason (sell ladder /
  trailing stop / stop loss / rug sell / top-10 dump / manual sell),
  and the buy-time signal values (5-minute gain, 5-minute volume,
  buys vs sells, regime slow/trending) — plus a summary comparing
  LOSING buys vs WINNING buys (count, average 5-minute gain and
  volume at buy, regime split, average loss/gain). Signals and
  reasons are recorded on the trade from the filter build onward;
  older trades show them as unavailable, never guessed — the exit
  reason and bot for older trades are matched from the activity log
  (nearest row naming the same coin within 3 minutes) and fall back
  to unavailable when there is no match. The **buy filter** applies
  to the Scanner and Trenches buy paths (both scan the same feed):
  a coin is only bought when it shows a real signal — at least
  **$1,000 of volume in the last 5 minutes** AND **buys outnumbering
  sells in the last 5 minutes** AND a **signal of at least 5%**
  (the 3-minute gain for the scanner, the 5-minute gain for
  Trenches). Missing or unparseable signal data means NO buy
  (fail-closed); a filtered-out candidate is logged once per scan
  (`silent_skip`, naming the strongest rejected coin). The filter is
  rule keys, not constants — `buy_filter` on a trenches/scanner rule
  set: `min_volume_5m_usd` (0–1,000,000), `require_buy_dominance`
  (true/false), `min_signal_pct` (0.1–100) — validated fail-closed
  like every other rule, and tunable through the assistant
  (\"set the buy filter for bot Luna: min volume $5000, min signal
  6%\" — shown back, confirmed before it applies). Existing
  Trenches/Scanner bots pick up the defaults on their next scan.
  Defaults were chosen from what the app already treats as a real
  signal: $1,000 absolute 5-minute volume (a real crowd moving
  money, not a $50 blip that still \"surges\" 2x against a dead
  hour), buys > sells (the regime test's buy-dominance test), 5%
  (the scanner's own buy trigger; Trenches' 3.4% bar is raised to
  5% unless tuned down). The analysis section on the Logs page is the tuning source:
  if the losing buys show a different pattern, change the rule keys
  — the defaults are a starting point, not a verdict.
- **Logs page (`/logs`, Page 11)**: the user's activity/trade log
  (latest 100 entries, newest first, active mode only) plus the
  losing-buy analysis (paper mode only). The old P&L dashboard
  (`/pnl`) was deleted 2026-11-10 — the portfolio chart now lives in
  the home balance area (candlestick, with duration options), and
  per-coin P&L is on the Coins list and coin detail pages. The chart
  is built ONLY from recorded snapshots (`portfolio_snapshots`,
  written on every silent-loop evaluation and after every paper
  trade) — history is never invented, and a range with no snapshots
  says "no data yet". Holdings with no current price are valued at
  cost and flagged "price unavailable", never guessed.
- **Pump.fun trading wallet**: pump.fun has no separate accounts, so
  trading on pump.fun uses a Solana wallet. At signup the user's app
  wallet is recorded as their pump.fun trading wallet
  (`users.pumpfun_wallet`, backfilled for older accounts) and shown on
  the wallet screen as "Pump.fun trading wallet". No new wallet is
  created — it is the same app wallet, linked for pump.fun trading.
- **Dedicated signing bot + support ID (`tradingbot/signing_bot.py`,
  `tradingbot/executor.py`, `tradingbot/pumpfun.py`)**: every account
  gets ONE dedicated signing bot at signup (backfilled for older
  accounts), with an immutable 8-digit support ID shown on the
  dashboard and in settings, labelled for tech support. There is no
  route, form, or code path that can change it — the only write to
  `signing_bots` is the INSERT at signup/backfill. The signing bot
  executes real trades on **devnet only** through the pump.fun
  bonding-curve program (`6EF8rrecthR5Dkzon8Nwu78hRvfCKubJ14M5uBEwF6P`,
  verified executable on devnet; its global account parses to the
  known constants). Buys and sells are built from the live bonding
  curve with a 1% slippage limit; the wallet key is decrypted
  transiently, used for one signature, and dropped. Guards: silent=1,
  mode=real, NETWORK=devnet, rules engine allows the trade, amount
  within buy-size % and balance (plus a 0.001 SOL fee reserve).
  Mainnet — or any other network — refuses loudly and signs nothing.
  The executor builds ONLY pump.fun buy/sell instructions (plus a
  create-ATA for the user's own token account); it never builds a
  transfer, withdrawal, or any other destination, enforced by an
  allowed-program check before signing. Manual real buys still refuse
  plainly ("Real token buying is not live yet") — real execution
  happens only through silent bots. Every signed trade is logged with
  signature, bot, coin, amount, rule, and signing-bot support ID.
  No live devnet trade has been run yet — that is a separate smoke
  test, after the owner's confirmation.
- **Railway provisioning (gated, off by default)**: `tradingbot/
  railway_provision.py` can create a per-user bot service via Railway's
  public GraphQL API, but only when `RAILWAY_PROVISIONING=1` AND
  `RAILWAY_TOKEN` are both set. It is never wired into signup and never
  runs in tests. It logs/returns only service and variable NAMES, never
  values. **Per-user bot provisioning consumes Railway credits — nothing
  spins up without an explicit admin action.**

## Deploy to Railway (admin)

1. Create the GitHub repo (James creates it — the Muse GitHub App
   cannot create repos) and push this directory to `main`.
2. In Railway, create a project from that repo (Nixpacks detects
   `requirements.txt` + `Procfile`; start command `python run.py`).
   No Dockerfile needed; no native build tools required.
3. Set service variables (names only — values are yours):
   `SESSION_SECRET`, `ENCRYPTION_KEY`, `NETWORK=devnet`.
   Optional: `RPC_URL`, `DATABASE_PATH`, `PAPER_START_CASH`,
   `ADMIN_USERNAME` (who may see `/admin/donations`; default is the
   first registered user).
   **Required for real trades and donations:** `FEE_RECIPIENT_PUBKEY`
   — the one wallet that receives the 3.65% trading fee and all
   donations. Without it, real trades refuse and the donate flow
   refuses plainly; there is no fallback wallet.
   Leave `RAILWAY_PROVISIONING=0` (default) unless you deliberately
   enable per-user bot provisioning — each provisioned service costs
   Railway credits.
4. Deploy. Check `/health` returns `{"ok": true, "network": "devnet"}`.
5. Silent trading loop: set `SILENT_LOOP_ENABLED=1` on the web service
   to run the loop as a daemon thread inside the web process (interval
   `SILENT_LOOP_INTERVAL_SECONDS`, default 60). The start command stays
   `python run.py`. A separate worker service is NOT used: the SQLite
   file lives on the web service's volume and a second service cannot
   see it. `python -m tradingbot.silent_loop --once` runs one iteration
   standalone (for smoke tests and a future shared-database setup).
   The loop only ever trades for bots the user explicitly switched to
   silent; it re-reads the flag every iteration, so turning silent off
   stops the bot on the next tick.
6. Passkeys (optional, but required for the passkey ceremonies to
   verify — without them the browser rejects the ceremony). Set these
   service variables on the live domain:
   - `WEBAUTHN_RP_ID` — the site's domain, e.g.
     `solentry-production.up.railway.app`
   - `WEBAUTHN_RP_NAME` — shown to the user, e.g. `SolEntry`
   - `WEBAUTHN_ORIGIN` — the full origin, e.g.
     `https://solentry-production.up.railway.app`

Notes: the SQLite file lives on the service disk (ephemeral on Railway
redeploys unless a volume is attached — attach a Railway volume at the
`DATABASE_PATH` location before real users sign up). For mainnet, set
`NETWORK=mainnet` only on explicit config, after a devnet shakedown.

## Live price feed (WebSocket)

One feed serves the whole app (`tradingbot/livefeed.py`): the server
subscribes to upstream sources, validates every tick, and pushes
validated ticks to browsers over the app's own WebSocket at `/ws/live`
(login required). Pages subscribe to the coins they show; prices,
holdings values, P&L, 1h/24h %, and the coin-detail chart update live
without a reload. If the socket drops, the page falls back to polling
`GET /api/live?coins=...` every 10 seconds and says so in the status
pill. The older per-page REST tick endpoint (`/api/coins/<id>/tick`)
is kept as a second fallback. Every displayed price shows its source
and last-updated time (hover any live number); a stale tick is dimmed
and labelled with its age, never shown as fresh.

**Sources (all free, no key):**

| Source | What it feeds | How |
|---|---|---|
| Kraken public WebSocket (`wss://ws.kraken.com`) | BTC / ETH / SOL majors | live ticker subscription |
| DexScreener public REST | pump.fun mint prices + 1h/24h changes | polled every 5s for watched mints |
| Jupiter lite-api v3 (`lite-api.jup.ag/price/v3`) | SOL cross-check | polled every 60s; used only if Kraken SOL is stale/missing, or logged as a warning if the two disagree by >5% |
| CoinGecko REST | fallback only (free tier is rate-limited) | the pre-existing price path, unchanged |

**Left out, on purpose:** Binance — its public REST and WebSocket
both return HTTP 451 from US IPs, and Railway runs in US East, so
Binance cannot serve this app. DexScreener's own WebSocket streams
only token profiles, boosts, and takeovers — not pair prices — so
mint prices are polled, not streamed. PumpPortal's WebSocket
(`wss://pumpportal.fun/api/data`) streams new-token events live and
works without a key; it is a candidate real-time mint source for a
later step (it needs per-mint trade subscriptions plus reconnect
handling, which the current poll already covers).

**Tick validation — why a bad price can never again inflate a
balance:** every tick is checked against the last good price for
that coin before it is used or shown. A single tick jumping more
than **50%** is rejected and logged, and the last good price stands.
A genuine step change is still picked up: three consecutive ticks
agreeing at the new level (within 5% of each other) re-base the
reference. Non-positive and non-finite prices are always rejected.
Data goes stale **30 seconds** after its last good tick. The same
validation gates the silent loop: prices and trenches data are
sanitised before evaluation and before a portfolio snapshot is
recorded, so a rejected tick can never become a trade signal or a
spiked balance — the $709,599.60 incident (one bad print, one
minute) cannot recur through this path. The portfolio chart is still
snapshot history: it updates when the loop records snapshots, not
tick-by-tick.

Kill switch: `LIVE_FEED_ENABLED=0` stops the upstream threads; the
app keeps serving from the existing REST feeds. No new secret is
needed — every source above is keyless.

## Candlestick charts (Page 5 + home balance chart)

The coin detail page (Page 5) shows a real candlestick (OHLC) chart
by default, with a button in the corner of the chart switching to the
regular line chart — both views are drawn from the same candles, so
they can never disagree, and the choice is remembered for the page
view. The homepage balance area has the same toggle on a compact
portfolio chart, with duration options (1h / 1d / 1w / 1m / 1y /
all-time). The chart does **not** redraw every second: the live
price number still updates per tick, but the chart re-renders at
most once per candle interval (fresh SVGs from
`GET /api/coins/<id>/candles?range=...`), and the caption says when
it last refreshed.

**Candle sources, in order:**

| Chart | Candles come from | Interval |
|---|---|---|
| Page 5, known coin | CoinGecko OHLC endpoint (`/coins/{id}/ohlc`) | set by CoinGecko's granularity (30 min for the 24h range, 4h for 1w/1m) |
| Page 5, pump.fun mint | the live feed's recorded tick history (in-memory, ~2,000 ticks per coin) | 1 min (24h) / 15 min (1w) / 1h (1m) / 1d (1y, all-time) |
| Home portfolio | the recorded portfolio snapshots (1-minute, the app's only portfolio history) | 5 min (1h) / 1h (1d) / 6h (1w) / 1d (1m) / 1w (1y) / 1d or 1w (all-time, by span) |

Candles are never faked: fewer than two candles draws nothing, and
the page says plainly that candles are still building (mints with
no feed history yet) or that there is not enough history yet (home
chart in a thin range). A mint's candles only exist while the app
has been running long enough to record them — a fresh deploy starts
with no mint history. The coins list (Page 4) shows every coin's
name and its ticker in its own span, so a long name can truncate
but the ticker never can; held mints show their real name + symbol
from the DexScreener feed when it names them, and the honest
"Pump.fun token …" label when it does not.

## Trading fees (3.65% of every trade)

Every trade — paper and real — pays a **3.65% fee**. On devnet a
real trade's fee is split in the same transaction: **1.7% of the
trade to the treasury** (the recipient in the `FEE_RECIPIENT_PUBKEY`
env var — James's own wallet, set in Railway) and **1.95% burned**
to the Solana incinerator. The fee is charged going
forward only: trades that happened before the fee landed are
never charged, and every user's fee total starts at zero.

- **The fee recipient** is configured, never generated: the app
  reads `FEE_RECIPIENT_PUBKEY` at runtime (a valid base58 32-byte
  Solana address). The same single wallet also receives all
  donations from the login screen. There is no app-generated
  Treasury wallet any more — any `treasury_wallet` row left from
  before is purged at startup and nothing ever writes one. If the
  var is unset, empty, or invalid, real trades refuse loudly
  before anything is signed — never a fallback wallet, never a
  guessed address. The recipient address is never shown in full
  on any page, API, or public surface, and is never in code or
  the repo. The in-memory copy is held in a mutable buffer and
  wiped in place the moment a transaction is built/sent; it is
  never logged.
- **Paper trades:** the fee is deducted from the trade value in the
  paper ledger (a $10 buy buys $9.635 of coins; a sell returns the
  proceeds minus 3.65%) and recorded in `trade_fees` with its SOL
  equivalent at the trade-time SOL price. The fee is shown in the
  buy/sell confirmation and the trade log.
- **Real (devnet) trades:** the fee is taken in SOL in the **same
  transaction** as the trade itself — TWO System-program transfers,
  appended after the pump.fun buy/sell instruction: **1.7% of the
  trade to the fee recipient (the treasury — James's own wallet)**
  and **the rest, 1.95% of the trade, burned** to the Solana
  incinerator (`1nc1nerator11111111111111111111111111111111`), a
  well-known unspendable address. Exact integer math (treasury =
  amount x 170 // 10000, fee = amount x 365 // 10000, burn = fee -
  treasury). Either the whole transaction confirms (trade + both
  transfers) or neither happens, so a fee is never taken from a
  trade that did not execute, and never twice for one trade (fee
  rows are unique per trade signature). **The burn is devnet-only:**
  it is gated on the app network being devnet, so this build can
  never burn on mainnet. The signing bot's destination restriction
  keeps exactly two exceptions for this: a System-program
  instruction is allowed only when it is one of the two fee
  transfers — treasury to the fee recipient for exactly the
  treasury lamports, or burn to the incinerator for exactly the
  burn lamports, each appearing exactly once. Any other transfer,
  destination, or amount is still refused (see
  `executor._check_instructions_only_allowed`). The 3.65% is a
  MOCK for the real mainnet total: pump.fun's fee (~1.9%) +
  SolEntry's fee (1.7% of the trade).
- **Home page:** the fees section shows the logged-in user's OWN
  total fees paid in SOL as a clickable dropdown listing their fee
  payments (coin, fee in SOL, date, signature where it is a real
  trade), with the live SOL price beside the total ("—" when the
  feed has no SOL price, never guessed). There is NO app-wide
  total on the home page, and the recipient address is never
  shown. The figure refreshes **every 5 seconds** while the
  homepage is open, from one lightweight `GET /api/fees` per tick;
  the poll stops when the page is hidden or closed, and a failed
  fetch shows "—", never a guessed number. Deleting a bot does not
  erase its fees: the fee rows stay (detached from the deleted
  bot) so the user's total still counts what was actually paid.
  The fees display shows THREE numbers, per user and app-wide
  (`/api/fees` carries all six): the **SolEntry fee** (1.7% of the
  trade), the **pump.fun fee** (the actual program fee paid on
  each trade, derived from the trade's amounts and the live
  global fee_bps — never the ~1.9% estimate), and the **burned**
  amount (1.95% of the trade). A dropdown switcher in the fees
  card flips the view between the SolEntry fee balance and the
  pump.fun fee balance (the closed control shows the current
  selection + a chevron; pressing it drops down the 2 options);
  the burned amount stays visible alongside, not part of the
  dropdown.
- **Mainnet rule:** when the app launches on mainnet, after
  selling a coin the proceeds are converted to SOL and held as
  SOL — never cash, never USDC. On devnet this is already how
  sells settle: pump.fun pays SOL to the seller's wallet, so there
  is no cash leg to convert. **Mainnet fee model (James,
  2026-11-11 — for the record, a launch-time change, not this
  build): on mainnet the app fee is 1.9% of the trade, ALL of it
  to the Treasury dev wallet (FEE_RECIPIENT_PUBKEY — the address
  James already supplied; no new wallet). Pump.fun's fee is
  separate (taken by pump.fun via the program, accurately
  accounted in the display). No burn on mainnet.**

## Security rules (do not weaken)

- Never log, print, or return a private key, password, session secret,
  encryption key, or token value.
- Never store a secret in code or in the repo. `.env.example` has
  placeholders only.
- Never move real SOL on an ambiguous instruction. Sends always need
  the confirm step.

## Security — how the app protects wallets (plain words)

No app is unhackable, and this one does not claim to be. What it does:

- **Passwords are irreversibly hashed** (scrypt, per-user salt). A
  stolen database gives an attacker hashes, not passwords.
- **Wallet keys are encrypted at rest** (AES-256-GCM, key from the
  `ENCRYPTION_KEY` env var only — never in code or the repo).
- **Keys are wiped from memory the moment a transaction is done.**
  The key is decrypted into a mutable buffer, used for one signature,
  and overwritten with zeros in a `finally` block — on success,
  refusal, or failure. It is never kept between trades, never
  logged, never returned, never stored in plain text. (One honest
  exception: the Phantom platform wallet's private key is shown to
  its owner exactly once, at creation, so it can be imported into
  Phantom — after that it is gone, by design.)
- **Transactions are confirmed on-chain before they count.** A trade
  or send is only recorded as done after the chain confirms it, and
  every transaction is verifiable by its signature on the explorer.
  Nothing is ever faked.
- **The signing bot can only sign trades it builds itself** (pump.fun
  buy/sell, plus creating the user's own token account). An
  allowed-program check before signing excludes the System program
  entirely, so a plain transfer or withdrawal can never be signed by
  the bot. Silent bots only trade within their rules and limits.
- **Anti-bot at the door:** rate limits on login (5 wrong tries lock
  an account 15 minutes; 20 failed tries from one address are
  blocked), signups, sends, and bot creation; a burst guard on
  sensitive endpoints (429 past 120 POSTs/minute from one address);
  a hidden honeypot field on login/signup that only bots fill; and
  Cloudflare Turnstile (see below) when its keys are set.
- **Sessions:** HttpOnly + SameSite=Lax cookies (Secure over HTTPS),
  12-hour lifetime, and the session is rotated on every login, so a
  stolen pre-login session is useless.
- **Security headers on every response:** Content Security Policy
  (only our own files, a per-request nonce for the two inline
  scripts, and Cloudflare's challenge scripts), HSTS, no framing,
  no MIME sniffing.
- **Daily send cap:** at most 5 SOL per wallet per day by default
  (`DAILY_SEND_LIMIT_SOL` — change it in Railway variables). A
  compromised session cannot drain a wallet in one day.
- **Anomaly detection:** repeated failed logins from addresses an
  account has never logged in from lock the account for 15 minutes
  and write a suspicious-activity audit row.
- **Audit log:** every wallet action (sends, trades, key operations,
  mode changes) is written to the activity table with the client IP
  and device behind it.

Honest limits, already told to James: encryption that must be USED
cannot be literally irreversible — the server has to unlock the key
for a split second to sign. What is irreversible is the password
hash. And "Bitcoin safety" means the Solana equivalent: signed with
the wallet's own key, confirmed on-chain, immutable afterwards.
